Abstract
CampusConnect is a web-based platform that connects students seeking internships and 
jobs with companies looking to hire student talent. Built using PHP, MySQL and a responsive 
HTML/CSS front end, the system supports two user roles — students and companies — each 
with dedicated registration, login and dashboard experiences. Students can build a profile, 
browse and search job listings, apply with a cover letter, and track the status (pending, accepted 
or rejected) of every application they submit. Companies can post job or internship openings, 
review incoming applications alongside applicant resumes and profiles, and accept, reject, or 
reset the status of each application. The system uses PHP sessions for authentication and role-
based access control to keep student and company areas separate and secure. This report 
documents the design, implementation and testing of the working system.

CampusConnect – A Student–Company Job and Internship Platform
Chapter 1: Introduction
1.1 Background
Placement and internship coordination in colleges is often handled through fragmented, 
manual channels such as notice boards, emails and spreadsheets. This makes it difficult for 
students to discover timely opportunities and for companies to reach suitable student candidates 
efficiently. General-purpose job portals exist, but they are not tailored to the simpler, two-role 
(student and company) workflow that a single college’s placement activity typically needs. 
CampusConnect was built as a lightweight, self-contained web application to address this gap 
for a college setting.
1.2 Objectives
To design and develop a web-based platform where students can register, build a 
profile, discover and apply to job and internship postings, and track the status of their 
applications; and where companies can register, post job openings, and review, accept or reject 
student applications.
1.3 Purpose, Scope and Applicability
1.3.1 Purpose
The purpose of CampusConnect is to simplify how students discover and apply for jobs 
and internships, and how companies advertise openings and screen candidates, by bringing 
both sides of the process into a single, unified system rather than relying on scattered manual 
coordination.
1.3.2 Scope
The system covers registration and login for both student and company roles, profile 
management, job posting and browsing with search/filter, applying to jobs with a cover letter, 
and application status tracking and management (pending, accepted, rejected) for both students 
and companies. It does not cover payment processing, automated resume parsing or scoring, or 
interview scheduling.
1.3.3 Applicability
The system is applicable to any college or training-and-placement cell that wants a self-
hosted, lightweight application to coordinate job and internship opportunities between its own 
students and recruiting companies, without depending on a large third-party job portal.

Chapter 2: Survey of Technologies
Several technology options were considered for each layer of CampusConnect before 
settling on the final stack.
Front End
Plain HTML and CSS were chosen over a JavaScript framework such as React or 
Angular. For a project of this scope — a defined set of server-rendered pages per role — a front-
end framework adds build tooling and configuration overhead without a matching benefit. Plain 
HTML/CSS keeps every page simple to write, style and test directly in the browser.
Back End
PHP was chosen over alternatives such as Node.js/Express, Python/Django or Java 
Servlets. PHP integrates directly with the Apache web server and MySQL database with no 
additional runtime or framework to install, provides built-in session handling that is used 
throughout CampusConnect for authentication, and is well documented — a practical choice 
for a single-developer academic project on a fixed timeline.
Database
MySQL (via MariaDB) was chosen over alternatives such as PostgreSQL or SQLite. It 
is the database bundled by default with XAMPP, has mature support for relational schema 
design with foreign keys — used throughout the CampusConnect schema — and is 
administered easily through phpMyAdmin, which was used throughout development to design 
and verify the database structure.
Development Environment
XAMPP (Apache + MySQL/MariaDB + PHP) was chosen as the local development 
and hosting environment because it bundles all required services, avoiding separate installation 
and configuration of Apache, PHP and MySQL individually. Visual Studio Code was used to 
write and edit all PHP, HTML and CSS files.

3.1 Problem Definition
The overall problem is that students and companies lack a simple, shared platform for 
discovering and applying for internship and job opportunities, and for managing those 
applications afterwards. This can be divided into two sub-problems: (a) students need a 
structured way to find opportunities, apply to them, and check the outcome of each application; 
and (b) companies need to publish openings and efficiently review, accept or reject applicants 
after viewing each applicant’s profile and resume.

3.5 Preliminary Product Description
CampusConnect is a two-role web application. A student can create an account, 
maintain a profile describing their course, college, graduation year, skills and resume, browse 
and search active job listings posted by companies, and apply to any listing with a cover letter. 
Every application a student submits can later be tracked from a dedicated My Applications 
page, which shows its current status. A company can create an account, maintain a company 
profile, post job or internship listings, and manage every application received against its own 
listings — viewing the applicant’s profile and resume before accepting, rejecting, or resetting 
an application back to pending.

CampusConnect follows a three-tier architecture. The client tier is the web browser, 
which sends HTTP requests (GET / POST) to the application tier, where the Apache web server 
runs PHP 8.2 and holds the business logic. The application tier sends SQL queries, written as 
prepared statements, to the data tier — the MySQL / MariaDB database campusconnect_db — 
and receives the result set, which is returned to the browser as an HTML / CSS response. The 
whole stack runs locally on the XAMPP server package.

4.2.2 Data Integrity and Constraints
•
id columns in every table are auto-incrementing primary keys.
•
students.user_id is a foreign key referencing users.id (fk_students_user), ensuring every 
student profile belongs to a real user account.
•
jobs.company_id is a foreign key referencing companies.id (fk_jobs_company).
•
applications.student_id
 
and
 
applications.job_id
 
are
 
foreign
 
keys 
(fk_applications_student, fk_applications_job) ensuring every application references a 
real student and a real job.
•
companies.email carries a UNIQUE index, preventing duplicate company email 
addresses at the companies table level.
•
Every column across the schema is NOT NULL except applications.updated_at, which 
defaults to NULL until an application’s status is first changed.
•
Passwords are never stored in plain text — they are hashed with PHP’s 
password_hash() before being inserted, and verified with password_verify() at login.
•
The relationship between users and companies is not enforced by a database foreign 
key; it is matched at the application level by comparing users.email = companies.email 
in the PHP code.

4.3.2 Data Structures
The application relies mainly on three PHP data structures: associative arrays returned 
by mysqli’s fetch_assoc() to hold a single database row (e.g. a job, a student profile, an 
application); indexed/associative arrays built from fetch_all() equivalents (via while loops) to 
hold a full result set such as a list of jobs or applications; and PHP’s built-in $_SESSION 
superglobal array, which stores user_id, name and role for the duration of a logged-in user’s 
browser session and is read on every protected page to enforce access control.
4.3.3 Algorithms Design
Login algorithm:
1. Read email and password from the submitted form.
2. Look up the user record in the users table by email.
3. If no matching record: show “Invalid email or password”.
4. If the account status is not “active”: show “Your account is not active”.
5. Else, verify the submitted password against the stored hash using password_verify().
6. If verified: store user_id, name and role in $_SESSION, then redirect to the student or 
company dashboard based on role.
7. If not verified: show “Invalid email or password”.
Apply-for-job algorithm:
1. Confirm the logged-in user is a student; otherwise redirect to login.
2. Load the job by job_id; if not found or inactive, show an error.
3. Check whether an application already exists for this (student_id, job_id) pair.
4. If it exists: show the current status instead of the form.
5. Else: display the cover-letter form.
6. On submit, validate the cover letter is at least 50 characters.
7. If valid: insert a new row into applications with status = pending.
8. Redirect the student to the My Applications page.
Accept / reject application algorithm:
1. Confirm the logged-in user is a company; otherwise redirect to login.
2. Read application_id and the requested status from the request.
3. Update the applications row ONLY IF its job_id belongs to a job posted by the logged-
in company (ownership check via a join through the jobs table), preventing one 
company from changing another company’s applications.
4. Set status to the requested value (accepted / rejected / pending) and update updated_at.
5. Redirect back to the Job Applications page.

Every page in CampusConnect follows a single, consistent design system built on a

4.5 Security Issues
•
Passwords are hashed using PHP’s password_hash() (bcrypt) and verified with 
password_verify() — plain-text passwords are never stored or compared.
•
Every database query uses mysqli prepared statements with bound parameters 
(bind_param), which prevents SQL injection from user-supplied input.
•
Every protected page begins by checking $_SESSION["user_id"] and 
$_SESSION["role"], redirecting unauthenticated users or users of the wrong role to 
login.php.
•
Server-side ownership checks (e.g. matching a job’s company_id to the logged-in 
company, or an application’s student_id to the logged-in student) ensure a user can only 
act on records that belong to them, rather than relying only on hiding UI elements.
•
User-supplied output (names, job titles, cover letters, etc.) is escaped with 
htmlspecialchars() before being rendered into HTML, mitigating cross-site scripting 
(XSS).
•
Resume uploads are restricted to PDF, DOC and DOCX files, limited to 5 MB, and 
stored under a randomly generated filename (uniqid()) rather than the original uploaded 
filename.

student trying to open a company-only page). The full set of test cases and their results is

5.2.1 Code Efficiency
Prepared statements are used for every query that includes user-supplied values, which 
both prevents SQL injection and allows the database to reuse the same query plan across 
repeated calls to structurally identical statements (e.g. the same application-status update 
running for many different applications). Queries select only the columns actually needed by 
the page rather than using SELECT *, and MySQL automatically indexes primary-key and 
foreign-key columns, keeping the join-heavy queries used throughout the project — such as the 
applications listing that joins jobs, students and users — efficient at the scale of data a single 
college would generate.

Chapter 7: Conclusions
7.1 Conclusion
CampusConnect successfully delivers a working, two-role web platform that lets 
students discover and apply for jobs and internships, and lets companies post openings and 
manage the applications they receive. Every core feature identified in the requirements — 
registration, authentication, profile management, job posting and browsing, applying, and full 
application-status management — was implemented, tested, and confirmed working, as 
demonstrated by the test cases in Chapter 5 and the screenshots in Chapter 6.
7.1.1 Significance of the System
The system gives a small college a self-hosted, lightweight alternative to informal, 
manual placement coordination. Beyond its practical use, the project also demonstrates applied 
full-stack web development skills: relational database design with proper keys and constraints, 
server-side validation and session-based authentication, role-based access control, and a 
consistent, responsive user interface.
7.2 Limitations of the System
•
The password-reset flow only verifies that the user knows the account’s registered 
email address; it does not send a real, time-limited reset link by email, since that would 
require configuring external SMTP infrastructure not available in this local academic 
setup.
•
There is no dedicated administrator panel to moderate job postings or manage user 
accounts directly at the database level.
•
Resumes are stored on the local server’s filesystem rather than a dedicated cloud storage 
service.
•
The internships database table exists but is not yet wired into any part of the application 
(see Section 4.2.1).
•
The system has been tested locally on XAMPP and has not yet been deployed to a public 
web server.

login.php
Purpose: Authenticates a user with email and password and redirects to the student or 
company dashboard.
<?php
session_start();
require_once "config/database.php";
 
$message = "";
 
if ($_SERVER["REQUEST_METHOD"] === "POST") {
    $email = trim($_POST["email"]);
    $password = $_POST["password"];
 
    $stmt = $conn->prepare(
        "SELECT id, name, password, role, status
         FROM users
         WHERE email = ?"
    );
    $stmt->bind_param("s", $email);
    $stmt->execute();
    $result = $stmt->get_result();
 
    if ($result->num_rows === 1) {
        $user = $result->fetch_assoc();
 
        if ($user["status"] !== "active") {
            $message = "Your account is not active.";
        } elseif (password_verify($password, $user["password"])) {
            $_SESSION["user_id"] = $user["id"];
            $_SESSION["name"] = $user["name"];
            $_SESSION["role"] = $user["role"];
 
            if ($user["role"] === "student") {
                header("Location: student/dashboard.php");
                exit;
            }
 
            if ($user["role"] === "company") {
                header("Location: company/dashboard.php");
                exit;
            }
        } else {
            $message = "Invalid email or password.";
        }
    } else {

            $message = "Resume must be smaller than 5 MB.";
            $resumeValid = false;

            $resume = uniqid("resume_", true) . "." .
                strtolower(pathinfo($_FILES["resume"]["name"], PATHINFO_EXTENSION));

                );
            }
        }

            "UPDATE students
             SET course=?, college=?, graduation_year=?, skills=?, resume=?
             WHERE user_id=?"
        );
        $stmt->bind_param(
            "ssissi",
            $course, $college, $graduation_year, $skills, $resume, $user_id
        );
